# STORY-06：完成企业版发布验收

## 愿景

用户只安装一次 `dsh-auth`，就能得到登录能力和受管 Caddy。直接安装、私有镜像和离线归档都不需要第二个包或用户自己的网关。

## 范围

已发布的 `0.1.14` 没有完整 Caddy 运行时，不能满足自包含安装契约。本 Story 通过 `0.1.15` 向前修复：交付一个可独立安装的主包，并在同一候选上完成真实部署、登录、回滚、公开文档和供应链验收。完整架构和发布边界见 Epic 的[全局设计](../epics/EPIC-ONE-TIME-TOKEN-LOGIN.md#全局设计)；详细进度和证据只在[执行卡](../agent/STORY-06-完成企业版发布验收执行卡.md)维护。

## 关键决策

1. **只发布一个完整主包和一个 GitHub Release。**
   - 决定者：用户。
   - Agent 建议：最初建议两个独立 Caddy 平台包；用户发现主包将无法单独使用后否决。
   - 结果与影响：用户、私有镜像和离线归档都只需管理一个发布物。
2. **主包同时携带 Linux x64 和 ARM64 Caddy。**
   - 决定者：用户。
   - Agent 建议：将两种架构收入同一主包；用户采纳。
   - 结果与影响：主包会变大，但两种受支持机器可以使用同一安装物。
3. **生产安装过程不联网下载 Caddy。**
   - 决定者：用户。
   - Agent 建议：只在制作 Release 时取得并校验固定官方 Caddy；用户采纳。
   - 结果与影响：setup、私有镜像和离线安装使用同一内容。
4. **继续使用项目固定的标准 Caddy，不复用用户网关，也不恢复自研 Go Gateway。**
   - 决定者：用户。
   - Agent 建议：Caddy 负责 TLS、代理和连接，dsh-auth 负责认证业务；用户采纳。
   - 结果与影响：项目能固定边缘行为，不需要长期维护通用网关。
5. **不覆盖 `0.1.14`，只通过 `0.1.15` 向前修复。**
   - 决定者：用户。
   - Agent 建议：基于 npm 已发布版本不可替换，建议发布新补丁版；用户采纳。
   - 结果与影响：旧标签不移动；未经用户另行授权，不发布或弃用任何版本。

## 验收标准

- 用户只需安装或归档一个 `dsh-auth` 包，不需要任何 Caddy 配套包。
- x64 和 ARM64 使用同一主包；不支持的系统在修改主机前收到明确错误。
- 断网、私有镜像和本地文件安装都只使用主包内经过验证的 Caddy。
- npm 包与 GitHub Release 使用同一发布候选，版本、内容和校验结果一致。
- automatic/manual TLS、systemd/容器、密码/一次性链接登录都在当前 Harness 上通过真实验收。
- `0.1.14` 不覆盖、不移动标签；未经授权不弃用或发布版本。
- 所有安全和功能场景都在同一候选上通过后，RELEASE 才能成为 1/1。
