# 后续并行安排

## 结论

Story 的验收和合并顺序保持线性：`STORY-02 → 03 → 04 → 05 → 06`。公开 CLI、状态格式、令牌文件和会话语义逐层依赖，不能同时按不同假设实现。

可以在单个 Story 内并行。Story 负责人先冻结接口和文件边界，再把独立工作放入专用 worktree。各支线只合入当前 Story，不提前把后续 Story 标为完成。

## 可并行工作

| 阶段 | 主线 | 可并行支线 | 合并边界 |
| --- | --- | --- | --- |
| STORY-02 | v2 CLI、安装计划和执行/回滚 | Caddy 双平台包；systemd/doctor/E2E fixture；安装文档 | 先合平台包，再合安装器，最后跑同一提交的系统验收 |
| STORY-03 | token store 与签发命令 | 原子故障注入测试；权限/输出泄密测试 | token 文件契约冻结后开始；全部合回 STORY-03 负责人 |
| STORY-04 | POST 兑换、限流和会话 | fragment 桥接页与浏览器测试；Caddy access-log 验证 | 后端路由先合，页面和真实 E2E 后合 |
| STORY-05 | 首次设置状态转换 | 仅可并行准备场景 fixture 和文案测试 | 核心实现集中完成；它与 STORY-04 共改认证状态和页面，不并行开发 |
| STORY-06 | acceptance commit 冻结 | 锁定/latest Harness E2E、平台/systemd、打包/秘密扫描三组只读验证 | 所有组必须验证同一提交；任何修复都会撤销受影响结果 |

## 不并行的部分

- STORY-03 不在 STORY-02 合并前开始实现；它依赖最终安装状态和 CLI v2。
- STORY-04 不在 token 文件契约冻结前实现兑换；否则并发消费与失败语义可能分叉。
- STORY-05 不与 STORY-04 同时修改 `application`、认证状态或会话生命周期。
- STORY-06 不与产品代码修改并行；它只验收一个冻结提交。

建议最多同时使用三个开发支线。并行价值主要在 STORY-02、STORY-04 和 STORY-06；其余阶段保持单主线更快，也更少返工。
